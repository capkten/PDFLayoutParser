# PDFLayoutParser 1.0 设计稿

## 1. 背景

本项目目标是实现一个面向 **矢量 PDF** 的解析工具，使用 Python 将 PDF 中的版面元素解析为结构化结果，并支持三种输出方式：

- `JSON`
- `Markdown`
- `图片`

1.0 版本明确不做图片内容识别、OCR、图标语义识别等图像理解类能力。图片只作为 PDF 内嵌资源或页面渲染结果处理。
印章在 1.0 中只支持“给定坐标的资源提取”，不做自动检测或语义识别。

## 2. 目标

1. 解析矢量 PDF 中可提取的结构信息，包括文本、块、行、词、字符、表格、原始图片资源。
2. 输出以 `pages: [{...}]` 为核心的结构化 JSON，且 `pages` 中每一项代表一页。
3. 生成尽量保留标题、段落、列表、表格结构的可读 Markdown。
4. 支持两类图片输出：
   - 提取 PDF 内嵌原始图片资源，并保留坐标与资源信息
   - 根据页面坐标渲染整页图片，作为可视化输出
5. 印章支持基于给定坐标的资源提取，并在 Markdown 中保留占位
5. 在不引入 OCR 的前提下，尽量还原表格的行列与单元格合并关系。

## 3. 非目标

以下能力不纳入 1.0：

- 扫描件 OCR
- 图片语义识别
- 图标识别
- 印章识别
- 复杂多栏阅读顺序优化
- 页眉页脚自动剔除
- 语义级文档理解

## 4. 需求边界

### 4.1 输入

- 输入为单个 PDF 文件或批量 PDF 文件
- 重点支持由文本对象、路径、表格线、嵌入图片组成的矢量 PDF
- 对于无法解析字符级坐标的页面或片段，允许降级为 block / line / word 级输出

### 4.2 JSON 输出

JSON 顶层必须包含：

- `document`: 文档级元信息
- `pages`: 页面数组

页面内部必须包含：

- `index`: 页码，从 `0` 开始，和 `pages` 数组下标保持一致
- `size`: 页面宽高
- `rotation`: 页面旋转信息
- `blocks`: 版面块列表
- `tables`: 表格列表
- `images`: 原始图片资源列表
- `seals`: 印章资源列表
- `render`: 页面渲染图信息

文本层级按“能拿到就输出”的原则保留，其中 `char` 级信息在可用时必须输出：

- `block`
- `line`
- `word`
- `char`

如果某一层无法从 PDF 中稳定提取，则该层可以缺失，不强制补空数组。

### 4.3 Markdown 输出

Markdown 的目标是“可读、结构尽量保留”，而不是逐字平铺：

- 标题尽量按字号、位置、粗细等规则推断
- 段落按 block / line 组织
- 列表按符号、编号、缩进识别
- 表格尽量输出为 Markdown 表格
- 原始图片资源可用占位文本或引用方式保留

### 4.4 图片输出

图片输出分两类：

1. **原始图片资源导出**
   - 从 PDF 资源中提取图片文件
   - 记录所在页、bbox、资源索引、原始尺寸、输出路径

2. **页面渲染图导出**
   - 按页面坐标渲染整页
   - 用于预览、比对、人工校验布局结果

### 4.5 印章输出

印章只支持基于给定坐标的提取：

- 输入印章坐标后导出对应区域资源
- 保留所在页、bbox、输出路径等信息
- Markdown 中保留占位引用，例如 `[印章: page-1 seal-1]`

## 5. 推荐架构

1.0 推荐采用“`PyMuPDF` 为主，规则层补强”的混合方案。

### 5.1 为什么这样选

- `PyMuPDF` 能较稳定地提供页面文本、字符、图片资源、坐标和页面渲染
- 适合快速形成一个可用的 1.0
- 后续如果需要增强表格识别、阅读顺序或版式语义，可以在其上继续扩展

### 5.2 备选方案

- **单库方案**：只依赖 `PyMuPDF`
  - 优点：简单、快
  - 缺点：表格和 Markdown 结构还原效果有限

- **规则增强方案**：在混合方案上增加更多版式规则
  - 优点：输出效果更强
  - 缺点：调优成本高，1.0 容易过度复杂

## 6. 模块划分

建议拆成以下模块，每个模块职责单一：

### 6.1 `loader`

负责打开 PDF、读取文档级元信息、遍历页面。

输入：

- PDF 文件路径或文件对象

输出：

- 文档句柄
- 页面句柄
- 基础 metadata

### 6.2 `text_extractor`

负责提取文本结构：

- block
- line
- word
- char

同时尽量保留坐标、字体大小、字体名称、颜色、粗细等可用信息。
如果 PDF 能稳定提供单字坐标，则必须输出 `char` 级信息；如果不能，则允许只输出 `word` / `line` / `block`。

### 6.3 `layout_mapper`

负责把 `text_extractor` 输出的 block / line / word / char 层级，转换为项目内部统一的版面元素模型。

这个步骤不是简单的“原样透传”，而是要做结构归一化：

- 将文本层级映射为统一的 `layout element`
- 识别文本、表格、印章、图片等元素大类
- 为后续 JSON、Markdown、渲染输出提供一致的数据入口

### 6.4 `image_extractor`

负责提取 PDF 内嵌图片资源：

- 图片对象
- bbox
- 页面索引
- 资源索引
- 输出文件路径

### 6.5 `table_extractor`

负责识别候选表格区域，并尽量还原：

- 行
- 列
- 单元格
- `rowspan`
- `colspan`

### 6.6 `layout_builder`

负责把统一的版面元素组织成页面最终结构，并按版面顺序排列。

它消费的是 `layout_mapper` 之后的结果，而不是直接消费原始文本层级。

1.0 先采用“版面块顺序可用即可”的策略，不做复杂多栏重排。

### 6.7 `markdown_writer`

负责将结构化结果转换为 Markdown。

### 6.8 `json_writer`

负责输出统一 JSON 格式。

### 6.9 `render_engine`

负责页面渲染图导出。

## 7. 数据模型

### 7.1 文档级

```json
{
  "document": {
    "file_name": "sample.pdf",
    "page_count": 12
  },
  "pages": []
}
```

### 7.2 页面级

```json
{
  "index": 0,
  "size": {
    "width": 595.28,
    "height": 841.89
  },
  "rotation": 0,
  "blocks": [],
  "tables": [],
  "images": [],
  "render": {
    "path": "outputs/pages/page-000.png",
    "width": 1654,
    "height": 2339,
    "dpi": 200
  }
}
```

### 7.3 版面元素级

版面元素统一包含：

- `type`: `text` / `table` / `seal` / `image` / `separator`
- `bbox`
- `order`
- `content`

文本类元素内部再按需承载：

- `spans`
- `lines`
- `words`
- `chars`

### 7.4 表格

表格建议表示为：

- `bbox`
- `rows`
- `cols`
- `cells`
- `confidence`
- `source`

其中单元格建议保留：

- `row_index`
- `col_index`
- `rowspan`
- `colspan`
- `bbox`
- `text`

## 8. 处理流程

推荐的处理顺序如下：

1. 打开 PDF
2. 遍历页面
3. 提取页面文本结构
4. 提取字符级信息，若可用则保留
5. 将文本层级映射为统一版面元素
6. 提取原始图片资源及坐标
7. 识别表格候选区域并重建单元格
8. 按版面块顺序聚合页面内容
9. 生成 JSON
10. 生成 Markdown
11. 渲染页面图片
12. 导出原始图片资源

## 9. Markdown 生成规则

### 9.1 段落

同一块内连续行优先合并为段落，保留换行仅用于结构分隔。

### 9.2 列表

识别常见列表特征：

- `-`
- `*`
- `+`
- `1.`
- `1)`

对明显缩进项也应尝试识别为列表项。

### 9.3 表格

如果表格结构足够完整，输出 Markdown 表格。
如果表格无法完全重建，则输出结构化占位块，并保留原始单元格信息在 JSON 中。

### 9.4 图片

Markdown 中图片和印章都直接使用标准图片语法，例如 `![alt](path)`。
这样生成后的 Markdown 可以被常见渲染器直接显示。

## 10. 表格识别策略

1. 先用线条、文本对齐、空白间距寻找表格候选区域
2. 再将候选区域切分为行列网格
3. 基于文本框归属关系填充单元格
4. 基于边界缺失、跨列文本宽度、连续空白等信号推断合并单元格
5. 当无法稳定识别时，允许降级为“弱结构表格”，但保留 bbox 和原始文本顺序

1.0 的原则是“尽量还原”，不是“强制完美重建”。

## 11. 错误处理与降级策略

- 某页无法解析时，允许单页失败，不影响整份文档
- 某层级信息缺失时，向下级别降级输出
- 表格识别失败时，保留文本和 bbox，不阻塞其他输出
- 图片导出失败时，不阻塞 JSON / Markdown 生成

## 12. 性能与可扩展性

1.0 不优先做极致性能优化，但应满足以下基本要求：

- 支持按页流式处理，避免一次性加载全部大对象
- 输出路径、渲染参数、表格策略应可配置
- 后续可在不破坏 JSON 结构的前提下增加 OCR、图像识别、多栏阅读顺序等能力

## 13. 测试策略

建议建立以下测试集：

1. 普通矢量文本 PDF
2. 含表格的合同/报表 PDF
3. 含大量嵌入图片的矢量 PDF
4. 含字符级坐标但块结构复杂的 PDF
5. 无法稳定提取字符级信息的退化 PDF

测试重点：

- JSON 结构是否稳定
- Markdown 是否可读
- 表格是否能保留基本结构
- 原始图片资源是否能导出并带坐标
- 页面渲染图是否与页面坐标一致

## 14. 交付标准

1. 能输出统一 JSON，顶层为 `pages:[{}]`
2. 能输出可读 Markdown，并保留尽量多的标题、段落、列表、表格结构
3. 能导出 PDF 原始图片资源及其坐标
4. 能按页面坐标渲染整页图片
5. 能对常见矢量 PDF 给出稳定、可复现的结构化结果

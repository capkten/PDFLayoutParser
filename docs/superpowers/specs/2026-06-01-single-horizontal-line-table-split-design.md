# 单横线表格强切分设计

> 目标：对于表格区域内只有一条明显横线的情况，强制以这条横线作为表头和表体的分界线。横线上方只允许进入表头处理，横线下方只允许进入表体处理，避免表头合并逻辑污染表体内容。

## 背景

在当前项目中，财报类表格经常同时包含：

- 多级表头
- 分组表头
- 行内换行的列名
- 左侧锚点列

对于这类表格，如果只依赖当前 `text_alignment` 或单纯的词块聚类，表头与表体很容易被混在一起。特别是在 `page-046` 这类页面里，表头和表体之间有一条非常明确的横线，人工阅读时这条线就是结构分界。

因此，这里定义一个更强的规则：

- 如果表格区域内只有一条明显横线
- 那么该横线就是表头与表体的强边界
- 表头归并、分组头提升、rowspan/colspan 修复，只能在横线上方进行
- 横线下方的内容一律视为表体，不允许被表头合并逻辑吸收

## 目标

1. 正确切分表头和表体
2. 防止表头合并规则污染 body 行
3. 保持表体原有行顺序和列归属
4. 对横线上方的碎裂表头做有限归并
5. 不引入页码特例，不写死某一页

## 非目标

1. 不在 `table_extractor` 中重写表格发现逻辑
2. 不对所有复杂财报表做整表重建
3. 不尝试修复没有明确单横线分界的表格
4. 不更改 `Table` / `Cell` 的数据模型

## 设计原则

1. **横线优先**
   - 结构判断以横线为准，不以文本相似度为准。

2. **边界硬切分**
   - 横线以上和横线以下是两个不同的结构区域。

3. **表头只在上方处理**
   - 任何表头碎片合并、分组表头提升、列名拼接，都只发生在上半区。

4. **表体保持原样**
   - 横线以下的 body 行不参与表头归并。

5. **结构层实现**
   - 该规则属于表格结构处理，不属于表格边界发现。

## 适用范围

适用于以下场景：

- 表格区域内只有一条明显横线
- 横线上方是表头带，横线下方是表体带
- 上方可能存在分组表头或多行列名
- 下方存在稳定的正文数据行

不适用于：

- 没有明确横线分界的表格
- 多横线、多层边框、复杂网格表
- 需要重新推导列骨架的表

## 处理流程

### 总流程

```text
输入 Table + Page
  |
  v
识别表格内部的单根横线
  |
  v
按横线切分成 header band 和 body band
  |
  v
header band 内做表头归并 / span 修复
  |
  v
body band 保持原始行列归属
  |
  v
输出统一的 Table
```

### 1. 识别单根横线

结构处理层需要从页面几何信息中识别这条线，要求：

- 线横跨表格主体宽度
- 线位于表格内部，而不是页面装饰线
- 表格区域内没有第二条同等级的横向分界线

如果无法稳定识别这条线，就不启用该模式，退回普通表格处理。

### 2. 按横线切分区域

一旦识别出横线，就把表格内容切成两个 band：

- `header band`
  - 横线上方的文本与单元格
  - 允许多行
  - 允许分组表头

- `body band`
  - 横线下方的文本与单元格
  - 保持原始正文行结构
  - 不参与表头归并

### 3. Header band 内部处理

header band 只允许做以下动作：

- 合并同一列上下拆开的列名
- 识别分组表头，如 `本年金额`
- 识别左侧锚点列，如 `项目`
- 修正 `rowspan` / `colspan`

header band 不允许：

- 引入 body band 的词块
- 把 body 行的数值拼进表头
- 用宽松的 bbox 距离规则跨越横线合并

### 4. Body band 保持原样

body band 中的行必须保持：

- 原始 row 顺序
- 原始列顺序
- 原始数值归属
- 原始空单元格语义

这意味着：

- `追溯调整前余额` 不能被抬到表头
- `追溯调整` 不能被并入 header
- `追溯调整后余额` 不能因为上方表头修复而丢失

## 对下表的预期结果

针对 `page-046` 的下方表，单横线强切分后应得到：

- `项目` 保持在第一行第一列
- `本年金额` 保持为分组表头
- `年初归属于母公司所有者权益总额` 只作为表头碎片在 header band 内修复
- `追溯调整前余额`、`追溯调整`、`追溯调整后余额` 保持为 body 行
- body 行中的各列数值不被表头逻辑污染

## 结构判定建议

为了减少误判，建议同时满足以下条件才启用单横线模式：

1. 横线位于表格中部，而不是顶部或底部装饰线
2. 横线上方文本明显偏表头风格
3. 横线下方存在稳定的正文数值列
4. 表头区和表体区的纵向间距符合财报表格习惯

如果条件不充分，则回退到现有普通表格结构处理。

## 实现边界

该能力应该放在：

- `table_structure_rules` 或同级结构后处理模块
- 不放在 `table_extractor` 的表格发现阶段
- 不放在 `markdown_writer`

原因是：

- `table_extractor` 负责“发现表”
- 这里负责“解释表内结构”
- 输出层不应该反推表结构

## 测试策略

### 必须覆盖的测试

1. `page-046` 下表应被切分为 header/body 两个 band
2. header band 内的 `项目` 和 `本年金额` 结构正确
3. body band 中的 `追溯调整前余额` 不丢失
4. body band 中的 `追溯调整` 和 `追溯调整后余额` 不错位
5. 普通无横线或多横线表格不受影响

### 回归关注点

- 表头与表体不要互相吸收文本
- 不要让 body 的数值进入 header
- 不要让 header 的碎片扩展到 body
- 不要破坏普通表格的输出结构

## 验收标准

当以下条件同时满足时，认为设计达成：

- 单横线表格能够强制切分 header/body
- 下表 body 行不再被表头污染
- `page-046` 下表的 `项目`、`本年金额`、`追溯调整前余额` 都在正确位置
- 普通表格输出不回归
- 没有任何页码硬编码

## 总结

这条规则的核心不是“再做一次聪明的重建”，而是：

> 既然表格里已经有一条明确的结构横线，就把它当成硬边界。横线上方做表头，横线下方做表体，二者严格隔离。

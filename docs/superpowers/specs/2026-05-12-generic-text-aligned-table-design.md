# 通用文本对齐表格设计方案

## 背景

当前项目已经可以完成 PDF 文本解析，并通过 `TableExtractor._extract_via_lines()` 处理有线表格。该路径依赖可见横线和竖线，现阶段已经较稳定。

在 `152590_20230428_N7ZK_0.pdf` 中，从第 52 页开始存在大量不满足“完整网格线”条件的表格，包括：

- 三线表；
- 有横线但无竖线的表格；
- 主要依赖文本对齐表达结构的表格。

此类表格无法被当前线框建格逻辑稳定识别，`PyMuPDF.find_tables()` 在这些页面上也没有返回可用结果。

本方案的目标是在不改动现有有线表格逻辑的前提下，引入一条更通用的“文本对齐型表格”处理能力，用统一方法覆盖三线表、横线弱表格和完全无线表格。

## 范围

本方案覆盖以下类型的表格：

- 有完整横线和竖线的普通表格：继续由现有有线逻辑处理；
- 三线表：有少量横线、几乎无可用竖线；
- 有横线、无竖线的表格；
- 完全无线、主要依赖文本对齐表达列结构的表格。

本方案首版重点处理：

- 机器生成 PDF；
- 文字坐标可稳定获取；
- 列结构主要由重复对齐关系构成；
- 复杂表头、多层表头、跨列表头。

本方案暂不覆盖：

- OCR 图片表格；
- 纯扫描件；
- 几何和文本信号都极弱、无法和正文区分的自由排版列表；
- 强依赖业务语义模板的专用规则。

## 设计原则

- 保持现有有线表格逻辑不变；
- 将新增能力设计成独立分支，不污染现有线框建格链路；
- 优先保证精确率；
- 使用通用几何、排版、文本对齐信号，不依赖财报词典；
- 先发现候选表格区域，再在区域内部建表，避免全页直接跑激进文本推断；
- 区域内允许使用“真实线 + 文本虚拟线”的混合策略。

## 核心思路

参考 `pdfplumber` 的方法，可以把表格识别看作“先得到边，再由边恢复单元格和表格”。边并不一定都来自真实线条，也可以来自文本对齐所隐含出的虚拟线。

但我们不直接照搬其“整页找边 -> 整页建格”的方式，而是增加一个更保守的前置阶段：

1. 先发现高置信候选表格区域；
2. 在候选区域内部，根据表格样式选择横向策略和纵向策略；
3. 生成真实边与虚拟边；
4. 恢复单元格、表头结构和最终表格。

这样既能借鉴 `pdfplumber` 的通用性，又能减少在整页正文上直接跑 `text + text` 带来的误判。

## 总体架构

`TableExtractor.extract()` 建议保持三层结构：

1. `_extract_via_lines(page)`
2. `_extract_via_text_aligned_regions(page)`
3. `_extract_via_pymupdf(page)`

说明：

- 第 1 层保持现状，不修改现有有线表格逻辑；
- 第 2 层是新增通用分支，负责三线表、无线表格、文本对齐表格；
- 第 3 层保留现有回退逻辑。

新增分支识别出的表格统一使用：

- `source="text_aligned"`
- 现有 `Table.rows`、`Table.cols`、`Table.cells`
- 现有 `Cell.rowspan`、`Cell.colspan`

## 新分支的内部流水线

建议将新增分支拆成 5 个阶段：

### 1. `_find_table_candidate_regions(page)`

作用：

- 基于混合版面信号，找出高置信候选表格区域。

输出：

- 候选区域 `bbox`
- 区域级特征
- 区域级置信度

### 2. `_collect_region_words(page, region_bbox)`

作用：

- 从候选区域内提取词级对象，保留位置、尺寸、文本等信息。

### 3. `_collect_text_rows(words)`

作用：

- 将候选区域内的词聚成视觉行，为后续列推断和横向边推断提供基础。

### 4. `_build_region_edges(rows, region_features)`

作用：

- 在区域内部，根据样式选择横向和纵向策略，生成真实边和虚拟边。

### 5. `_build_table_from_region_edges(rows, edges, region_bbox)`

作用：

- 从区域级边结构恢复单元格；
- 构建复杂表头；
- 输出最终 `Table`。

## 候选表格区域发现

这一步是整条新分支的关键。目标不是“把所有表格都找出来”，而是先找出“足够像表格”的区域，再在这些区域里做更激进的结构恢复。

区域发现必须有一组明确的硬性指标，否则整条分支会过度依赖启发式，难以控制误判。

### 候选区域的输入信号

区域发现不再只依赖横线，而是结合多类通用信号：

- 页面中的横线、细矩形、短边框；
- 文本行密度；
- 多行之间重复出现的列对齐位置；
- 行间距的稳定性；
- 区域整体的矩阵化覆盖范围；
- 文本块与正文段落在宽度、断行方式上的差异。

### 候选区域的硬性指标

候选区域至少应满足以下硬性条件中的大部分，首版建议将其作为强约束而不是软打分：

- 至少有 `3` 行有效文本行；
- 至少有 `2` 个由多行共同支持的稳定列轴，首选 `3` 个及以上；
- 参与列轴支持的有效行数占候选区域文本行数的比例不低于某个阈值，例如 `60%`；
- 候选区域的横向覆盖宽度明显大于普通段落缩进宽度，例如覆盖页宽的一定比例；
- 至少存在一个连续的“重复结构段”，即连续多行在列数、列轴位置、对齐模式上相近；
- 如果区域内存在横线、细矩形或分隔带，则作为加分项，但不再作为必需项。

如果一个区域无法同时满足“稳定列轴 + 连续重复结构”这两个核心条件，则不进入后续建表阶段。

### 适合当作候选表格区的强信号

- 连续多行文本在多个稳定 `x` 位置重复对齐；
- 行宽覆盖较大，明显不是单栏段落；
- 区域内存在多行相似结构，行与行之间更像“记录”而不是自然语言换行；
- 行距相对稳定；
- 存在少量横线或横向分隔带，进一步增强表格可能性；
- 顶部若干行可能形成表头，下面多行形成重复数据结构。

### 应当拒绝或降权的信号

- 大部分行只有 1 个长文本块；
- 各行的 `x` 分布漂移很大，没有重复列轴；
- 文本更像自然语言句子、注释或段落说明；
- 行数太少，无法形成稳定结构；
- 区域宽度很窄，更像普通缩进列表或标题说明。

### 候选区域生成思路

建议做法不是先靠线切带，而是先从文本行结构出发，再用线做增强：

1. 全页提取词级对象；
2. 将词聚成视觉行；
3. 在连续多行中寻找“重复列对齐模式”；
4. 将这些连续行合并成候选区域；
5. 若区域内有横线或分隔带，则提升置信度；
6. 若区域下方接说明性段落、`注：` 或自然语言块，则在结构断裂处截断。

这样做的结果是：

- 三线表可以被发现；
- 完全无线表格也有机会被发现；
- 横线只作为增强信号，而不是硬前提。

## 区域内文本行重建

在候选区域内，不应直接依赖现有 `Block` 结构，而应基于词级数据重建行。

建议的词模型：

- `text`
- `x0`
- `x1`
- `center_x`
- `y0`
- `y1`
- 可选的字体大小、字体名

建议的行构造方式：

- 通过 `y` 重叠或相近基线将词聚成视觉行；
- 每一行按 `x0` 排序；
- 每一行保留整体 `bbox`、词数、水平覆盖范围、数值词占比等统计信息。

这样做的原因是：文本对齐型表格经常在 PDF 内部被组织成一个或几个大文本块，如果直接依赖 `Block`，会丢失真实列结构。

### 候选区域的推荐判定方式

首版建议采用“两阶段判定”：

1. 先做快速筛选
   - 全页按连续文本行滑窗；
   - 找出出现重复列轴和重复行结构的窗口；
   - 将相邻窗口合并为较大候选区域。

2. 再做严格确认
   - 检查区域内有效行占比；
   - 检查列轴支持度；
   - 检查是否存在明显正文段落特征；
   - 检查区域底部是否已退化成说明文本。

只有通过严格确认的区域，才进入下一阶段。

## 区域内混合边策略

这是和上一版方案相比最大的变化。区域内部不再预设“横线驱动”，而是对横向和纵向分别选策略。

### 横向策略

横向策略决定如何构造行边界，建议支持：

- `lines`
  - 使用区域内真实横线；
  - 适合三线表、横线表格。

- `text`
  - 使用文本行的 `top` / `bottom` 推断虚拟横边；
  - 适合完全无线表格。

- `hybrid`
  - 真实横线优先，文本行边作为补充；
  - 适合横线不完整、只有局部分隔的表格。

### 纵向策略

纵向策略决定如何构造列边界，建议支持：

- `text`
  - 基于词的左边界、右边界、中心点的重复对齐推断虚拟竖边；
  - 这是文本对齐型表格的主策略。

- `explicit`
  - 当表头或某一局部区域能稳定给出列坐标时，可直接使用明确列边；
  - 适合从表头恢复全表列结构。

- `hybrid`
  - 先用文本推断列轴，再结合少量真实竖边或局部边界修正；
  - 适合某些半有线、半无线样式。

### 首版建议的样式映射

- 有线表：仍由旧分支处理，等价于 `lines + lines`
- 三线表：`vertical=text`，`horizontal=lines`
- 有横线无竖线：`vertical=text`，`horizontal=hybrid`
- 完全无线：`vertical=text`，`horizontal=text`

## 列轴推断

列推断的目标不是让每一行独立分列，而是为整个候选区域推断一套全局稳定列轴。

### 锚点提取

对每个词项，提取多种列锚点：

- `left_anchor = x0`
- `right_anchor = x1`
- `center_anchor = (x0 + x1) / 2`
- `token_type = text | numeric | mixed`

原因：

- 文本列更适合看左对齐；
- 数值列更适合看右对齐；
- 居中表头更适合看中心点。

### 数值列的特殊对齐特征

对于金额、比例、单价、数量等数值列，还应额外利用一类强特征：

- 小数点对齐；
- 万位分隔符对齐；
- 同位数数值在右侧边界上的稳定对齐。

这类对齐在财务报表、统计表、清单类 PDF 中都很常见，而且通常比普通文本列更稳定。

因此在提取锚点时，除了 `right_anchor` 和 `center_anchor` 之外，建议补充数值列识别和数值格式特征：

- 判断一个词项是否为数值型文本；
- 判断其是否包含小数点；
- 判断其是否包含千分位分隔符；
- 记录其小数点的视觉位置；
- 记录其最后一个数字字符的右边界位置。

如果多个数值词在某个候选列上表现出明显的小数点对齐或分隔符对齐，应将该列轴视为高可信列轴。

### 候选列轴聚类

在候选区域内：

- 对所有锚点值做一维聚类；
- 每个聚类中心视为候选列轴；
- 统计该列轴被多少行支持；
- 记录该列轴主要来源于左、右还是中心锚点；
- 允许对不同锚点类型赋不同权重。

对于数值列，建议额外提升以下锚点的聚类权重：

- 具有稳定 `right_anchor` 的金额列；
- 具有稳定小数点位置的数值列；
- 具有稳定千分位分隔节奏的数值列。

原因是这类列的几何锚点最不容易漂移，一旦识别出来，往往比文本列更适合作为全局列轴的“硬参考”。

### 列轴裁剪

需要剔除不稳定或噪声列轴：

- 只在极少数行中出现的弱列轴；
- 与更强列轴距离过近的冗余列轴；
- 只存在于说明性段落、未进入重复表格结构的列轴。

如果某个列轴同时满足以下条件，则应优先保留，即使它的文本覆盖行数略少于普通文本列：

- 主要由数值型词项支撑；
- 数值词项之间存在稳定的小数点对齐或分隔符对齐；
- 与相邻列轴的几何边界清晰分离。

也就是说，数值列的稳定对齐特征可以作为列轴保留和排序时的增强信号。

最终得到：

```python
col_guides = [g0, g1, g2, ...]
```

### 从列轴推导列边界

列边界建议通过以下方式得到：

- 相邻列轴中点作为默认分隔；
- 两端向候选区域边界扩展；
- 如某一列大量文本明显越过默认边界，可局部放宽；
- 但不能破坏全局列顺序。

## 横向边推断

为了支持完全无线表格，横向边不能只来自真实横线。

### 基于文本行的虚拟横边

可从文本行中生成两类横边：

- 行顶部边；
- 行底部边。

这样做的价值在于：

- 可以捕获最后一行；
- 可以为完全无线表格形成足够的行分隔结构；
- 与 `pdfplumber` 的 `horizontal_strategy="text"` 思路一致。

### 真实横边与虚拟横边融合

建议规则：

- 如果真实横线存在，优先保留；
- 如果真实横线缺失某些行边，则由文本行边补充；
- 如果真实横线和文本行边非常接近，则合并为单一横边；
- 如果真实横线与文本行结构明显冲突，以区域整体重复结构为准，而不是盲从某条孤立短线。

## 单元格恢复

对于文本对齐型表格，首版不应把“交点法”作为主建格方法。原因很直接：

- 无线表格中的边大多是虚拟边；
- 一旦行列推断本身存在偏差，交点法会把误差放大为大量错误原子 cell；
- 这会导致后续归并成本很高，而且难以稳定回收。

因此，首版建议采用“矩阵法优先，交点法仅作辅助手段”。

### 主方法：矩阵法

矩阵法的输入是：

- 全局叶子列边界；
- 行边界；
- 表头区层级信息；
- 每个词项到行列的归属。

建议过程：

1. 先根据全局列边界和行边界构建一个规则矩阵；
2. 每个矩阵格对应一个基础 cell；
3. 将词项填回各自所属的矩阵格；
4. 在表头区根据覆盖范围、父子关系和空洞情况合并矩阵格；
5. 生成最终带 `rowspan` / `colspan` 的 `Cell`。

这种方式更适合当前项目，因为：

- 它与“先推断列轴，再推断行边界”的思路一致；
- 即使虚拟边有轻微漂移，矩阵仍然相对稳定；
- 更容易控制复杂表头的归并逻辑；
- 更容易和现有 `Table` / `Cell` 模型对接。

### 辅助方法：交点法

交点法不作为首选，只在以下场景作为辅助验证或局部增强：

- 区域内真实横线很多，且部分真实边已经接近网格；
- 三线表中需要验证某些横向分隔是否足够稳定；
- 某一局部区域的虚拟边与真实边高度一致，适合用交点辅助确认。

也就是说，交点法在新分支中的定位应是：

- 用来辅助校验；
- 用来增强局部；
- 不作为整表主建格手段。

## 复杂表头处理

复杂表头属于首版范围内能力。表头恢复不建议使用“自上而下先猜父节点”的方式，而应优先采用“由下到上”的恢复路径。

### 表头区识别

在候选区域顶部，识别一个表头区，直到下方开始出现稳定重复的数据行模式。

可用信号：

- 顶部若干行的列占用模式变化较大；
- 下方连续多行开始共享类似列填充结构；
- 数值列在下方明显增多；
- 顶部存在居中对齐、跨列标题等特征。

### 为什么优先由下到上

用户提出的判断是合理的：表格下部，尤其是数据区和最靠近数据区的最后一层表头，通常结构最稳定；而越往上的表头合并越多、歧义越大。

因此首版建议：

- 先把最稳定的叶子列确定下来；
- 再从最靠近数据区的那一层表头开始恢复；
- 再逐层向上合并成父级表头。

这样能显著降低上层复杂合并对整表结构的污染。

### 由下到上的表头恢复流程

建议过程：

1. 先从数据区和靠近数据区的表头行中确定叶子列；
2. 将最下层表头文本先绑定到叶子列；
3. 对上一层表头文本，检查其水平覆盖范围是否完整覆盖多个相邻叶子列；
4. 若覆盖多个叶子列，则生成父级 `colspan`；
5. 若某个下层列在上层没有对应父节点，则向上保持空位；
6. 若某个表头在下层没有子项，但相邻位置存在更深层结构，则该表头向下生成 `rowspan`。

### 表头单元格生成

对于每个表头词组或文本块：

- 若只覆盖一个叶子列，生成普通 header cell；
- 若覆盖多个连续叶子列，生成 `colspan > 1` 候选；
- 若在更低层没有子项、而相邻列继续展开，则生成 `rowspan`。

### 父子关系恢复

建议按层自下而上恢复：

- 先识别最下层稳定叶子列；
- 再恢复其上一层父节点；
- 逐层向上做覆盖范围合并；
- 顶层最后形成完整表头树。

## 数据行建格

在叶子列和表头层级稳定后，数据行应采用保守建格策略：

- 词项按最接近且兼容的列轴归列；
- 同一行同一列中的词合并成一个单元格文本；
- 保留空单元格；
- 非表头区默认不主动创建 `colspan`，除非证据非常强。

这样有利于提升稳定性，避免把正文式换行误当成跨列结构。

## 输出兼容性

本方案不要求修改现有 schema。

### JSON

当前 `JSONWriter` 已能序列化：

- `Table`
- `Cell`
- `rowspan`
- `colspan`

因此，新分支只需正确填充现有模型。

### Markdown

当前 `MarkdownWriter` 已使用 HTML table 输出表格，并支持：

- `rowspan`
- `colspan`

因此，只要结构恢复正确，三线表和完全无线表格都可以被当前 Markdown 输出承接。

## 置信度与回退策略

由于精确率优先，新分支应有严格的输出门槛。

建议原则：

- 若有线表格分支已经返回可靠结果，则不进入新分支；
- 若候选区域未通过矩阵式结构校验，则不输出表格；
- 若区域内无法恢复稳定列轴，则不输出表格；
- 若最终建格结果退化得过于稀疏、碎片化或与文本矩阵特征明显冲突，则放弃；
- 若新分支未产出高置信度表格，则继续走现有 `PyMuPDF` 回退。

## 模块边界

以下内容不应改动：

- 现有有线表格几何线条提取逻辑；
- 现有有线表格区域构建逻辑；
- 现有表格输出 schema。

新增逻辑首版建议仍放在 `src/hexai_pdf_parser/table_extractor.py` 内，以多个小型辅助函数形式接入，保持阶段边界清晰。

如果实现后文件体积明显增长，再考虑把文本对齐型表格辅助逻辑拆到独立模块。该拆分不属于首版必需项。

## 测试策略

首版实现必须补充针对性测试，并优先动态构造 PDF。

### 单元测试

需要覆盖：

- 候选区域发现；
- 候选区域误判过滤；
- 文本行重建；
- 列轴聚类与裁剪；
- 横向虚拟边生成；
- 真实边与虚拟边融合；
- 复杂表头的 `rowspan` / `colspan` 恢复；
- 说明性段落截断。

### 集成风格测试

优先构造以下测试 PDF：

- 经典有线表格，确保不被新分支干扰；
- 三线表；
- 有横线、无竖线表格；
- 完全无线但列对齐稳定的表格；
- 多层表头 / 复杂表头；
- 表格后跟说明段落；
- 存在多列对齐但实际上不是表格的正文布局。

### 回归校验

由于旧逻辑必须保持不变：

- 现有 `tests/test_table_extractor.py` 中有线表格相关行为必须继续通过；
- 新增测试必须验证：当旧分支已成功识别表格时，新分支不会污染结果；
- 对文本对齐型样例页，应验证 `source`、`rows`、`cols` 以及关键 header cell 的 `rowspan` / `colspan`。

## 首版边界

首版明确要解决：

- 三线表；
- 有横线无竖线表格；
- 完全无线但对齐稳定的文本表格；
- 复杂表头和多层表头；
- 结构化 JSON 输出；
- 可读 Markdown 输出。

首版明确不扩展到：

- OCR 扫描表格；
- 语义模板驱动的业务专用规则；
- 与正文几乎无法区分的弱结构自由列表。

## 与 `pdfplumber` 思路的关系

本方案吸收 `pdfplumber` 的几个核心思想：

- 真实线和文本对齐都可以作为边的来源；
- 横向和纵向应分别选择策略；
- 文本列轴可通过词的左、右、中心对齐聚类得到；
- 文本行可用于补出虚拟横边。

但和 `pdfplumber` 不同的是：

- 我们不在整页直接跑激进的 `text + text` 建表；
- 我们先做候选区域发现，再在局部区域内部建表；
- 我们更强调高精确率和与现有流水线的兼容。

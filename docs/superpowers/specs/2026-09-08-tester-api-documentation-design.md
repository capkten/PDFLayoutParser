# 测试调用文档设计说明

## 1. 目标

更新现有 `docs/api-reference.md`，形成一份面向测试人员的、与当前源码一致的 PDFLayoutParser 调用文档。测试人员拿到文档后，应能够完成环境安装、命令行解析、Python API 调用、结果核对和问题定位，不需要先阅读项目内部实现。

## 2. 受众与范围

### 受众

- 主要受众：负责执行 PDF 解析测试、核对结构化结果和可视化结果的测试人员。
- 次要受众：需要在业务代码中集成 `PDFParser` 的开发人员。

### 范围

- 命令行入口及全部当前参数。
- Python `PDFParser` 的构造、完整解析、分阶段提取、区域提取、渲染和序列化接口。
- `ApiResult` 返回码和常见数据模型。
- 输出目录结构、关键 JSON 字段和测试核对项。
- 页码索引、归一化坐标、扫描版页面、模型路径和表格配置等容易误用的约束。
- 常见失败现象、调试命令和结果保留方式。

不在范围内：算法实现细节、内部模块开发指南、业务字段语义解释和与本项目无关的 PDF 编辑操作。

## 3. 方案选择

候选方案有三种：

1. 新建测试专用文档；内容集中，但会与已有 API 文档重复。
2. 只扩充 README；入口简单，但不足以支撑完整测试调用。
3. 更新 `docs/api-reference.md`，以它作为统一调用入口；能够复用已有内容并避免文档分叉。

采用第 3 种方案。正文按测试执行顺序组织：先安装和 CLI，再讲输出和返回契约，之后给出 Python API 与区域接口，最后提供验证清单和排障说明。

## 4. 正文结构

1. 文档定位、版本口径和适用范围。
2. 环境安装与最小可运行命令。
3. CLI 调用格式、参数表、常用场景和表格配置示例。
4. CLI 输出目录与文件含义。
5. Python API 构造函数和统一返回结果。
6. 完整解析、文本、表格、图片、页面渲染、JSON/Markdown 序列化。
7. 归一化区域接口和 `extract_table_structure`。
8. 数据模型及表格字段核对方式。
9. 测试执行清单、调试输出、性能输出和常见问题。

## 5. 当前源码口径

正文必须以当前实现为准，至少覆盖以下已确认接口事实：

- `ml_confidence` 默认值为 `0.40`。
- `PDFParser` 支持 `num_workers`、`backend`、`debug_pipeline`。
- CLI 支持位置参数或 `--pdf_path`，页码参数为 0-based。
- `parse(output_dir=...)` 会生成总 JSON、总 Markdown、逐页结果、页面 PNG、表格可视化 PNG、图片目录和 `timings.json`。
- `extract_table_structure` 返回带单元格四角坐标和字符级文本块的结构结果。
- `ApiResult.code` 为 `1`（有内容成功）、`0`（无内容但调用完成）或 `-1`（异常）。
- 区域接口使用相对于页面尺寸的 `0~1` 归一化坐标；单区域和多区域返回形态不同的接口要明确说明。
- 扫描页保留页面和渲染输出，但不进入普通文本、表格、图片和布局提取阶段。

## 6. 验证方式

文档完成后执行以下检查：

- 对照当前 CLI 参数和 `PDFParser` 方法签名逐项核对。
- 对照 pipeline 和 writer 的实际文件名核对输出目录示例。
- 使用项目内可用 PDF 做一次最小 CLI smoke test，确认命令和输出文件名可用。
- 使用 Python API 做一次解析与序列化 smoke test，确认返回码说明准确。
- 对 Markdown 做格式检查，并执行 `git diff --check`。

## 7. 交付约束

- 只修改调用文档和本次流程产生的设计说明，不清理工作区已有无关改动。
- 所有面向测试人员的说明使用中文；代码、命令、字段名保留原样。
- 不把实验脚本中的机器本地绝对路径作为测试前置条件，示例使用相对路径或占位路径。
